# Papersseum web app, first version: design

Date: 2026-10-13. Status: approved in conversation, pending review of this document.

## Goal

A website for the Papersseum season at IIITDM Jabalpur where students sign in
with their college Google account, upload a Python bot, watch it get validated,
and follow the ladder and match results. It runs against the real (local)
Supabase project; nothing is mocked.

## Constraints from the owner

- Minimal visual style, direction "A · Paper": off-white page, black text,
  1 px rules, plain tables. The only colour is the five player colours.
- No gradients, no animated or typewriter text, no badges, pills, tags, or
  decorative icons, plain buttons.
- Dark mode follows the visitor's system setting. No toggle.
- Sign-in is Google only.

## Pages

| Path | Content | Access |
|---|---|---|
| `/` | Hero (headline, one paragraph, Sign in with Google, Read the rules, season stats line), a board that replays a real recorded match on loop, top 5 of the leaderboard, 3 most recent finished matches | public |
| `/leaderboard` | Rank, bot, owner (or "house bot"), rating, Elo, ±, games, active version. Ranked by rating. Live | public |
| `/matches` | Newest first, 50 per page: match id, when, status, bots in finishing order | public |
| `/matches/[id]` | Round, finish time, duration, seed. One row per seat: slot colour, place, bot, coverage, deaths, strikes, finished/crashed, Elo before → after (+delta). Replay download link. Box saying the viewer isn't built yet | public |
| `/bots/[name]` | Owner, active version and since; rank, rating, Elo ± σ, games; Elo line over the last 100 matches; recent matches | public |
| `/me` | Own bot summary, upload form, list of own versions with live status | signed in, else redirect to `/sign-in?next=/me` |
| `/getting-started` | Static: install `papersseum`, `papersseum new`, writing an agent, `validate` / `play` / `eval`, limits (1 MB, 50 ms per move, 2 s reset, allowed imports, `load_weights`), uploading, how ranking works | public |
| `/sign-in` | One "Sign in with Google" button and an optional one-line error | public |

Every page has a header (Papersseum · Leaderboard · Matches · Getting started ·
Sign in or the user's handle) and a footer (season name, engine hash, sign out
when signed in).

Wording maps database terms to plain English. Submission status: `pending` /
`validating` → "Checking…", `active` → "Active", `rejected` → "Rejected",
`superseded` → "Replaced". Match status: `queued` → "Waiting", `running` →
"Playing", `done` → "Finished", `failed` → "Failed".

## Visual system

- Tokens are CSS custom properties defined for light and redefined under
  `prefers-color-scheme: dark`. Light: background `#fafaf8`, surface `#ffffff`,
  text `#111111`, muted `#666666`, rule `#e4e4e0`. Dark: background `#121212`,
  surface `#181818`, text `#e8e8e6`, muted `#9a9a9a`, rule `#2a2a2a`. Positive
  and negative Elo deltas use a muted green and red with enough contrast in both
  modes.
- Player colours by slot, same as `papersseum/render.py` `PLAYER_COLORS`:
  0 `#ff4d5e`, 1 `#4d9dff`, 2 `#35e07f`, 3 `#ffd23f`, 4 `#b36bff`. Shown as a
  9 px square with a 1 px rule-coloured border next to the bot name. Never the
  only carrier of information.
- Font: the scaffold's Geist Sans and Geist Mono. Mono only for code, seeds,
  file names and rejection reasons. Numbers use tabular figures.
- Buttons: primary is solid text-colour with background-colour text, 6 px
  radius. Secondary is a 1 px bordered surface button. Links are underlined.
- Layout max width about 960 px, 16 px side gutter on phones, tables scroll
  horizontally inside their own container on narrow screens (the page never
  does).
- The home page board replays one real recorded match on a loop (added
  2026-10-14 at the owner's request). A script in `web/scripts/` plays the
  match with the engine and saves it as a compact gzipped file of per-step cell
  changes plus head positions (about 130 KB). A small canvas plays it at real
  match speed (10 decisions per second, so 3 minutes), holds the final board
  for 3 seconds, then restarts. Paper colours, light or dark from the system
  setting. It pauses when off-screen or when the tab is hidden. No controls and
  no caption. Before it loads, without JavaScript, or when the visitor prefers
  reduced motion, the static SVG of one frame of the same match is shown
  (light and dark variants, also generated by a script).

## Architecture

Next.js 16 App Router (this repo's version: `proxy.ts` instead of middleware,
`cacheComponents: true`). Supabase via `@supabase/ssr` and `@supabase/supabase-js`.

### Supabase clients (`web/lib/supabase/`)

- `server.ts`: per-request server client using the publishable key and the
  visitor's cookies. Used by every page. Row-level security decides access.
- `browser.ts`: browser client using the publishable key, used only for
  Realtime subscriptions.
- `admin.ts`: secret-key client, starts with `import "server-only"`. Used only
  by the upload code. Never imported from client components.

### Rendering and data

- The static shell (header, headings, layout, fallbacks) prerenders. Every data
  read happens inside a component wrapped in `<Suspense>` with a quiet text or
  blank-row fallback, as Cache Components requires.
- Public reads go straight through the server client: `leaderboard` view,
  `bots`, `profiles`, `matches`, `match_players`, `season`, `rounds`.
- Match pages show no submission version for other players' bots, because
  `submissions` is readable only by its owner. Versions appear where they are
  public: `bots.active_version` / `leaderboard.active_version`.
- Replay link: the public URL of `replays/<replay_path>`.
- "Next round in N min": the next quarter hour (the `pg_cron` schedule is
  `*/15 * * * *`), hidden when `season.frozen`. Computed on the client so it
  never goes stale in a cached page.
- Times: relative ("4 min ago") under 24 hours, otherwise a short date.

### Live updates

Small client components subscribe to Supabase Realtime `postgres_changes`
(already published: `bots`, `submissions`, `matches`) and refresh their data:

- `/me`: `submissions` filtered to the user's bot. RLS ensures nobody receives
  other people's rows.
- `/leaderboard` and the home teaser: `bots` changes trigger a refresh.
- `/matches/[id]` while queued or running: that match's row.

If a subscription drops, nothing is shown; the page stays correct and catches
up on reconnect or reload.

## Sign-in

1. "Sign in with Google" posts a server action that calls
   `signInWithOAuth({ provider: "google", options: { redirectTo:
   <origin>/auth/callback?next=<path>, queryParams: { hd: <season domain>,
   prompt: "select_account" } } })` and redirects to the returned URL. PKCE is
   used; the verifier is stored in a cookie.
2. `app/auth/callback/route.ts` exchanges the code for a session and redirects
   to `next`. `next` is accepted only if it starts with `/` and not `//` or
   `/\`. A missing or rejected `next` means `/me`, so first-time users land
   on their bot page.
3. If Google or Supabase returns an error, redirect to `/sign-in?error=<kind>`.
   Supabase reports the database sign-up refusal as "Database error saving new
   user"; that maps to "Papersseum is only open to @<season domain> Google
   accounts." with the domain read from `season.allowed_email_domain`. Other
   kinds: cancelled, expired or invalid link, generic failure.
4. `proxy.ts` refreshes the session on each request (the `@supabase/ssr`
   pattern) and does nothing else. Pages check the user on the server with
   `getClaims()`. `/me` redirects to `/sign-in?next=/me` when signed out.
5. Sign out is a server action in the footer, then redirect to `/`.

### Supabase configuration changes (`supabase/config.toml`)

- Add `[auth.external.google]` with `enabled = true`,
  `client_id = "env(SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID)"`,
  `secret = "env(SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET)"`. The owner puts the
  values in `supabase/.env` (git-ignored).
- `[auth.email] enable_signup = false`, so Google is the only way to create an
  account. The admin API (used by `worker/scripts/seed_local.py` and the
  tests) is unaffected; this is checked during implementation.
- `additional_redirect_urls`: replace `https://127.0.0.1:3000` with
  `http://127.0.0.1:3000/auth/callback` and `http://localhost:3000/auth/callback`.

The owner already created a Google OAuth client (External, testing mode) with
redirect URIs `http://127.0.0.1:54321/auth/v1/callback` and
`http://localhost:54321/auth/v1/callback`.

## Upload

`web/lib/upload.ts` holds the logic as a plain server function,
`createSubmission(admin, userId, file)`, so tests can call it without a
browser session. The server action on `/me` gets the user from the session
and calls it. `next.config.ts` sets `experimental.serverActions.bodySizeLimit`
to `"2mb"` so a 1 MB file plus form overhead isn't rejected before our checks.

1. In the browser: refuse files not ending in `.py` or over 1,048,576 bytes
   before sending. The Upload button is disabled while pending.
2. On the server: require a signed-in user; re-check name, size (1 to
   1,048,576 bytes) and that the bytes decode as UTF-8; compute SHA-256.
3. Find the user's bot (`bots.owner_id`). Generate a submission id. Upload to
   `agents/<bot_id>/<submission_id>.py` with content type `text/x-python`, no
   upsert.
4. Call `api_create_submission(user_id, submission_id, path, sha256, size)`.
5. On a database error, delete the uploaded file, then map the error:
   PS001 → "Submissions are closed for this season.", PS004 → "You can upload
   again in <time from the error message>.", PS003 → "This bot is banned.
   Contact the organisers.", PS002 or anything else → "Upload failed, please
   try again." with details logged on the server only.
6. On success the new version appears as "Checking…" and Realtime flips it to
   Active or Rejected. Rejected rows show `error` and each entry of
   `violations` (`line N: detail`) in mono.

When `season.frozen`, the form is replaced by "Submissions are closed for this
season."

## Error handling

| Situation | Behaviour |
|---|---|
| Supabase unreachable or a query fails | That section shows "Couldn't load <thing>." with Try again; header and footer still render; details logged server-side only |
| Unknown bot name, non-numeric or missing match id | `notFound()`, plain 404 page with a link home |
| Match queued or running | "This match hasn't finished yet." and live refresh |
| Match failed | Seats without results, plus "This match couldn't be played: <matches.error>". No replay link |
| Empty data | One sentence per case (no bots, no matches, no uploads yet) |
| Season frozen | Upload replaced by a message; "next round" hidden |
| Banned bot | Profile says "This bot is banned."; the leaderboard view already excludes it |
| Sign-in errors | `/sign-in` with one line from the mapping above and the button again |
| Realtime drops | Silent; correct on reconnect or reload |

## Testing

- **Unit (Vitest)**: safe `next` check; file checks; error code → message
  mapping including the PS004 wait time; status wording; relative time;
  next-round calculation; Elo line scaling.
- **Upload against local Supabase (Vitest)**: create test users through the
  admin API, call `createSubmission` directly, and assert the storage object,
  the `submissions` row and the `validate` job exist; a second upload inside
  the cooldown is refused with the PS004 message and its file deleted; a
  frozen season is refused and cleaned up; another user's publishable-key
  client cannot read the submission.
- **CI**: a `Web` job in `.github/workflows/tests.yml` runs type check, lint,
  unit tests and `next build`. The Supabase-backed upload tests run in the job
  that already starts Supabase.
- **Manual**: real Google sign-in with a college account and with a non-college
  account (expect the refusal message). Every page checked in the browser in
  light and dark mode and at phone width during implementation.

## Out of scope

- Replay viewer for ladder matches (decision pending between worker-saved
  frames, a TypeScript engine port, or Pyodide). The home board's player is
  reusable for it once frames exist.
- Live play: matches are not streamed while they run; the worker only saves the
  replay at the end.
- Browser-driven end-to-end tests (Playwright).
- Editing handles or bot names, admin pages, notifications.
- Production deployment and the production Google OAuth client.
- The worker follow-up (full-match validation, heartbeat reconnect).
